## 2. 数据库模型

### 表：`logistics_shipments`

| 字段 | 类型 | 说明 | 来源 |
|------|------|------|------|
| shipment_id | VARCHAR(255) PK | 发货ID（唯一标识） | Excel |
| tracking_no | VARCHAR(255) | 货运单号 | Excel |
| forwarder | VARCHAR(255) | 货代名称 | Excel |
| shop_name | VARCHAR(255) | 店铺名称 | Excel |
| site | VARCHAR(50) | Amazon 站点（US/UK等） | Excel |
| fba_id | VARCHAR(255) | Amazon FBA 货件编号 | Excel |
| fba_warehouse | VARCHAR(255) | FBA 仓库 | Excel |
| manager_name | VARCHAR(255) | 负责人 | Excel |
| status | VARCHAR(255) | 货件在途状态 | Excel → 爬虫更新 |
| latest_info | TEXT | 货件状态备注 | Excel → 爬虫更新 |
| vessel_voyage | VARCHAR(255) | 船名航次 | Excel → 爬虫更新 |
| etd | DATE | 开船/起飞日期 | Excel → 爬虫更新 |
| eta | DATE | 到港时间 | Excel → 爬虫更新 |
| signed_at | DATE | 妥投日期 | Excel → 爬虫更新 |
| is_inspected | BOOLEAN | 是否被查验 | Excel → 爬虫更新 |
| raw_full_trace | TEXT | 完整物流轨迹 | 爬虫写入 |
| updated_at | TIMESTAMP | 最后更新时间 | 自动 |

## 3. 执行流程详解

### Step 1: `init_db()` — 数据库初始化
- 执行 `DROP TABLE IF EXISTS logistics_shipments CASCADE`
- 重新创建 `logistics_shipments` 表
- **设计原因**：Excel 是唯一数据源，每次运行都从最新 Excel 重建，数据库仅作临时缓存

### Step 2: `load_excel_to_db()` — Excel 数据导入
- 使用 pandas 读取 Excel 的"发货数据详情" sheet（header=1，即第 2 行为表头）
- 从第 3 行开始遍历数据行
- 通过 `clean_excel_data()` 清洗：NaN/None/空字符串 → Python None，布尔值标准化
- 将 15 个 Excel 列映射到数据库字段
- 逐行调用 `upsert_shipment()` 执行 `INSERT ... ON CONFLICT DO UPDATE`

### Step 3: `process_crawlers()` — 爬虫调度
- 调用 `get_pending_tasks()` 获取待处理任务：
  - 条件：`status != '签收' AND tracking_no IS NOT NULL AND latest_info != 'Done'`
- 按货代名称分组（`tasks_by_fw`）
- 启动一个 Chromium 浏览器实例（所有 Playwright 爬虫共享）
- 对每组货代任务：
  - **辰舟/欧杰**：创建 `LocalExcelStrategy` 实例，从本地 Excel 文件读取
  - **纽酷**：创建 `NiuKuSpider`（API 模式，不需要 page）
  - **其他（袋你飞/海桥/心达/丛林鸟/易派）**：
    - 创建新的浏览器 context
    - 实例化对应爬虫，传入 page 和凭证
    - 调用 `login()` → 遍历任务调用 `search(tracking_no)`
    - 每个结果调用 `update_tracking_info()` 更新数据库
  - 在 `finally` 中关闭 context

### Step 4: `analyze_logistics_exceptions()` — 异常分析
检测三类异常：

**A. 延期检测**（`today - ETA > 5 天`）
- US 站点的延期货件 → `us_exception_list`
- 其他站点 → 按负责人分组到 `other_exceptions`

**B. 查验检测**
- `is_inspected == True` → 按负责人分组到 `inspections`

**C. 延误检测**
- `latest_info` 包含"延误"、"延迟"或"延至" → 按负责人分组到 `delations`

### Step 5: `send_notifications()` — 钉钉推送
- US 站异常 → 发给 `US_SITE_MANAGER` 列表中的所有用户
- 其他站点延期/查验/延误 → 通过 `MANAGER_MAPPING` 查找负责人钉钉 ID，逐个发送私聊

### Step 6: `read_and_update_excel()` — 数据回写
- 使用 pandas 读取 Excel，提取所有发货 ID
- 查询数据库获取最新数据
- 使用 openpyxl 按列字母映射（AY-AZ-BC-BD-BE-BL-BG）写入 Excel
- 保存到输出路径

## 4. 通知机制

| 触发时机 | 位置 | 通知内容 | 接收人 |
|----------|------|----------|--------|
| 单条货件状态变更 | `database.py:update_tracking_info()` | 单号+店铺+新状态 | 对应负责人 |
| 批量异常汇总 | `main.py:send_notifications()` | 延期/查验/延误列表 | 负责人/US站点管理员 |

### 状态变更检测逻辑
```
1. 查询数据库中该货件的当前 latest_info
2. 与爬虫返回的新 latest_info 比较
3. 按 '————' 分隔符取第一段（去掉时间戳部分）进行对比
4. 如果不同且新值不为空 → 发送钉钉私聊通知
```

## 5. 爬虫技术细节

### Playwright 爬虫（5 家）
- 共享基类 `BaseSpider`：定义 `login()`、`search()`、`search_with_retry()`、`safe_wait()` 接口
- `search_with_retry()` 提供自动重试机制（默认 3 次）
- 每个爬虫独立实现：
  - **袋你飞**：Angular SPA，解析 9 个流程步骤
  - **海桥**：需处理滑块验证码（模拟鼠标拖拽）
  - **心达/丛林鸟**：同平台（nextsls.com），需关闭欢迎弹窗
  - **易派**：公开页面，在 iframe 内操作

### API 爬虫（纽酷）
- 纯 REST API，不使用 Playwright，**不继承 BaseSpider**
- JWT Token 认证，缓存 24 小时（`niuku_token_cache.json`）
- 三个接口：登录（`/login`）、订单详情（`/getFirstLegOrderDetail`）、物流轨迹（`/findLogisticsTrack`）
- 在 `main.py` 中通过特殊分支处理：直接调用 `spider.search()` 而非 `search_with_retry()`

### 本地 Excel 策略（辰舟/欧杰）
- 直接读取本地 Excel 文件，不使用浏览器
- 辰舟：通过 FBA ID 匹配，黄色背景单元格表示已送达
- 欧杰：通过发货 ID 匹配
